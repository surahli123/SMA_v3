## BLOCKER

**B1 — "Read-only" is an asserted design property, not an enforced one. No enforcement point is named.**
*Docs observed:* the only chokepoint is a logical component — `final-architecture-spec.md:159` ("Capability Broker | Allowlisted tool, adapter, scope, pagination, redirect, path, concurrency, timeout, cancellation, and budget enforcement") and the invariant at `final-architecture-spec.md:115` ("source adapters read only"). `final-architecture-spec.md:613` defers the actual mechanism: "Production credentials, identity mechanism, secret store, rotation/revocation … require the production-authority decision before implementation." The closest thing to an enforcement architecture lives in a non-authoritative research doc: `deepseek-harness-practices.md:232` ("non-replaceable broker outside Harness composition") and `deepseek-harness-practices.md:229` ("separate constrained process"), which `deepseek-harness-practices.md:302` itself labels "an **unfrozen engineering proposal**."
*Reviewer inference:* nothing in scope requires read-only credential scope (read replica, read-only DB role, read-scoped API token), network egress control, or a policy boundary in a different process/trust domain from the model. The broker sits in the Agent's own trust domain, so it is a code assertion an in-process defect or a prompt-influenced adapter can bypass. `final-architecture-spec.md:608` ("Source text … cannot change capabilities") is a requirement, not a mechanism. **An LLM plus an in-process allowlist is not a read-only system.**
*Correction before any production read:* make credential scope the primary control — per-source credentials physically incapable of write, issued to a broker process the Agent cannot execute arbitrary code in, behind an egress allowlist. P2 must produce a per-source write-denial receipt obtained with the real production credential.

**B2 — Whose identity the Agent reads with is undecided, and the ACL-diagnosis case is the hardest problem in enterprise search.**
*Docs observed:* ABSENT as a decision — searched `final-architecture-spec.md`, both wayfinder docs, `deepseek-harness-practices.md`, `enterprise-experiment-post-analysis-profile.md`. `final-architecture-spec.md:195` says every request carries "actor identity, authorization context" without saying whose. The intake only *asks*: `production-evidence-authority-intake.md:92` ("Which authorized test identities or aggregate counts may be used?"), `production-evidence-authority-intake.md:129`, and `production-evidence-authority-intake.md:93` (E12: "Under what purpose may raw content ever be read, by whom"). `production-evidence-authority-intake.md:171` implies synthetic identities ("Authorized-test receipt binding pseudonymous identity class") but that is an accepted *proof format*, not an access model.
*Reviewer inference — leak scenario:* Scenario A's own evidence plane requires ACL diagnosis (`final-architecture-spec.md:400`, "Eligible corpus, permission trimming, identity/ACL sync"). Diagnosing over-filtering requires comparing what different users could retrieve — i.e. reading across per-user permission-trimmed result sets. A service identity broad enough to do that sees documents no single reviewer is cleared for. The packet then renders them. `final-architecture-spec.md:610` reauthorizes render against "recipient role and scope"; `final-architecture-spec.md:609` and `final-architecture-spec.md:205` apply "permission intersection" **of the source records**, not of the reviewing human's entitlements against each document's ACL. There is no per-document, per-recipient ACL evaluation at render time anywhere in scope. A reviewer opening an M2 win/loss example (`enterprise-experiment-post-analysis-profile.md:204-215`) can therefore see result content from a corpus they cannot search. The authority is not scoped, not logged as an identity decision, not approved, and not time-bounded — `production-evidence-authority-intake.md:68` treats "approval and expiry" as an open question, not an answer.
*Correction:* decide the identity model explicitly (recommend: synthetic test principals for allow/deny probes, aggregate-only for cross-user comparison, no broad service identity over document bodies); require render-time per-document ACL evaluation against the recipient's live entitlements; time-box any elevated authority with a named approver and expiry.

**B3 — Append-only immutability vs. deletion/erasure obligations is never acknowledged.**
*Docs observed:* immutability is absolute — `final-architecture-spec.md:121` ("Append-only history"), `final-architecture-spec.md:162` ("No mutable update/delete API"), `freeze-canonical-domain-policy-contracts.md:289`. Retention is entirely UNKNOWN: `production-evidence-authority-intake.md:220` (D09), `production-evidence-authority-intake.md:127`. The nearest acknowledgement is a question, not recognition of a conflict: `production-evidence-authority-intake.md:132` ("Which digests or attestations are safe to retain when the underlying evidence must expire or be deleted?").
*Reviewer inference:* enterprise-search evidence contains queries, document text, and user/session data — subject to retention maxima and erasure requests. A sealed packet (`final-architecture-spec.md:642-655`) containing that content cannot be deleted by design. This is a legal conflict, not a design nit.
*Correction:* packets store pointers + keyed digests for any erasure-eligible class, content in a separately keyed store; define crypto-shredding (destroy the per-subject key, leave a tombstoned revision) as the deletion path; name the retention owner and maximum per artifact tier before any real read.

## MAJOR

**M1 — Redaction is specified for Trace only; the Evidence/packet path has a prohibition list and no mechanism.**
*Docs observed:* the Trace path is genuinely good — deny-by-default field allowlist before envelope construction (`deepseek-harness-practices.md:295`, `:302`, `:333`), canary tests (`deepseek-harness-practices.md:259`), and the correct principle "Bounding is not redaction" (`deepseek-harness-practices.md:350`). The canonical path has only `final-architecture-spec.md:612`, a list of things that "MUST NOT enter model context, Trace, logs, packets…", with no classifier, allowlist, schema-typed field policy, or fail behavior. `production-evidence-authority-intake.md:219` (D08) is UNKNOWN.
*Gaps even in the Trace path:* (a) unknown *fields* have no rule — `deepseek-harness-practices.md:329` handles unknown event kinds only, and hosts are explicitly unstable (`:307` Claude transcripts "internal and release-variable"; `:382` Cursor publishes no schema), so a new host version's field has undefined disposition; (b) canaries prove planted positives only — no sampling, no false-negative measurement, no requirement that the canary set be authored independently of the allowlist.
*Correction:* one schema-typed allowlist governing Evidence, packet, and Trace alike; unknown field → drop + Coverage Gap; uncertain classification → fail closed; a detector run reporting both planted-positive recall and a sampled false-negative estimate as a P2 artifact.

**M2 — Digests function as membership/confirmation oracles across tenants.**
*Docs observed:* `final-architecture-spec.md:205` forbids leaking "Logical identity, existence, digest, locator, and cardinality" across authorization boundaries, and `final-architecture-spec.md:611` forbids denial revealing existence — the right instinct. But `final-architecture-spec.md:439` *requires* config candidates to carry a "redacted value digest," and `production-evidence-authority-intake.md:44` records `content_digest: sha256:<digest>`. `production-evidence-authority-intake.md:87` still lists which config values are secret as UNKNOWN.
*Reviewer inference:* a plain SHA-256 of a low-entropy value (flag state, threshold, hostname, tenant name, short config string) is brute-forceable; a document digest lets anyone holding a candidate document confirm its presence in another tenant's case. The same oracle applies to `deepseek-harness-practices.md:337`'s "authorized integrity digest."
*Correction:* keyed HMAC with per-tenant keys for all content/value digests, or bucketed change-indicators for config; never a bare hash of source content.

**M3 — Authority-creep surfaces without hard limits.**
Adequate as written: retries are failure-typed with permanent-authz stop (`final-architecture-spec.md:686-687`); fallback needs a named alias/NONE and ceiling (`production-evidence-authority-intake.md:72`, `:204`); pagination expansion fails closed (`production-evidence-authority-intake.md:247`); workers draft only (`final-architecture-spec.md:363`, `:695`); shadow-read and replay are gated (`final-architecture-spec.md:671`, `:710`).
Unbounded or absent:
- **Semantic fan-out** — `final-architecture-spec.md:695` permits fan-out on "the unresolved branch" with no width/depth cap; every numeric budget is deferred (`final-architecture-spec.md:83`). Budget-exhaustion behavior exists (`final-architecture-spec.md:689`) but with no value, cost binds before authority does.
- **Cache warming / prefetch** — ABSENT; searched all five docs. Caches appear only in prohibition lists (`final-architecture-spec.md:612`) and as an unresolved retention tier (`production-evidence-authority-intake.md:220`). A prefetching adapter reads beyond the case's authorized scope and persists it.
- **Tool/adapter allowlist changes** — no approval requirement. `production-evidence-authority-intake.md:130` requires new approval for a tenant, source, role class, field, purpose, or retention period — not for adding a tool or adapter.
- **Trace troubleshooting re-open** — `deepseek-harness-practices.md:337`: "Separately authorized troubleshooting may re-open the original host source under its own ACL." No named approver, expiry, receipt, or logging requirement. A standing back-door to exactly the raw content the envelope exists to exclude.

**M4 — Third-party reuse: license handled, supply chain and data-flow review missing.**
*Docs observed:* licensing is correct — MIT, NOTICE retention, fork-from-fixed-SHA, auditable patch series (`deepseek-harness-practices.md:343`). Missing: (a) the review admits SHAs were never matched to signed tarballs, integrity digests, or SBOMs (`deepseek-harness-practices.md:276`), and the SBOM requirement at `:231` is scoped to plugins, not the forked code; (b) the reused parsers (`deepseek-harness-practices.md:349`, `:351`) were written for a single-user local machine and will now parse enterprise transcripts — no fuzz/malformed-input suite beyond line-skipping; (c) no transitive-dependency review of the fork; (d) **data flow** — passive collectors run on every engineer's Codex/Claude/Cursor host (`deepseek-harness-practices.md:307-308`) and feed a central store. That is a new enterprise-wide developer-monitoring pipeline. Cursor emits user email (`deepseek-harness-practices.md:308`, dropped by policy), but session-attributable engineer activity is still collected centrally. No doc names an employee-monitoring/DPIA/works-council review, or who may query the Trace store.

**M5 — P2 exit evidence is largely concrete, with three placeholders and a weak sign-off model.**
*Concrete enough to produce and check:* acknowledgement matrix with role, decision revision, time, intake digest (`production-evidence-authority-intake.md:277`); every E01–E14 field answered or `UNKNOWN` (`:246`); a redacted proof locator per canonical source (`:247`); complete and partial read receipts (`:249`); fallback named or `NONE` with ceiling (`:252`); D01–D15 resolved or explicitly blocking (`:257`); plus the ticket-level requirement that the Production Owner, each Eng Technical Owner, and the Security/Privacy Owner acknowledge their named rows (`:264-271`).
*Placeholders:* "versioned redaction and retention policies" (`production-evidence-authority-intake.md:268`) — no field taxonomy, no required classes, no schema; "purpose-bound read authorization" (same line) — no shape given; `content_digest: sha256:<digest-of-approved-redacted-artifact>` (`:44`) — presumes a redaction spec that does not exist (see M1).
*Sign-off weakness:* acknowledgements are by role (`production-evidence-authority-intake.md:18`) and may be "explicitly delegated" (`:245`). No named humans, no separation of duty, no non-delegable security/privacy acknowledgement, no expiry on the closure itself.
*What I would additionally require before any production read:* (1) per-source write-denial receipt from the real credential; (2) a written egress/network policy artifact; (3) the B2 identity decision plus a render-time document-ACL design; (4) the M1 redaction spec with detector results; (5) the B3 erasure design; (6) a data-flow inventory naming every store — workspace, Trace, cache, fixtures, packets, logs — with tenant partition key and retention per store; (7) a dated, named approval with ≤90-day expiry and defined re-approval triggers.

## Verdict on the gate

P2 is a **real gate with a real closure checklist** (`production-evidence-authority-intake.md:243-279`), and it correctly refuses to let repository research answer production questions (`:12`). But as written it certifies *paperwork about sources*, not *enforcement*. Every finding above is enforcement, not documentation: read-only mechanism, identity model, render-time ACL, redaction spec, erasure path, digest oracles, cache/prefetch, fan-out caps. None is currently a required exit artifact. **Do not grant production read access on the current checklist.**
